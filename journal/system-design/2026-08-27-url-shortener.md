## 1. Requirements

### Functional
<!-- ระบบต้องทำอะไรได้บ้าง -->
1. ให้ User นำ url มาใส่ แล้วแปลงเป็น short url ให้
2. จดจำ short url เพื่อแมพค่าให้ได้เป็น url จริงๆ

### Non-functional
<!-- availability? latency ที่ยอมรับได้? consistency แค่ไหน? -->
1. ไม่ควรใช้เวลานานในการหา url และไม่ควรรอนานเวลา rediract ไปยัง url shorturl ควรมีเวลาระยะหนึง ซึึงผมไม่รู้ว่าควรออกแบบไว้กี่ชัวโมง กี่วัน

### คำถามที่ควรถามคนให้โจทย์
<!-- ถ้านี่คือการสัมภาษณ์จริง จะถามอะไรก่อนลงมือ -->
1. Short URL ควรมีระยะเวลาเท่าไหร
2. ต้องการแสดง list url ทีมีไหม
3. User ที่ใช้งานมีกี่ประเภท

## 2. Capacity Estimation

> ทำขั้นนี้ **ก่อน** วาดสถาปัตยกรรม — ตัวเลขเป็นตัวกำหนดว่าออกแบบแบบไหนถึงจะพอ

| รายการ                     | ตัวเลข      | ที่มา / สมมติฐาน                                                                                                                   |
| :------------------------- | :---------- | :--------------------------------------------------------------------------------------------------------------------------------- |
| DAU                        | 100-200 คน  | คนที่เข้ามานำ URL ยาวๆ มาแปลงให้สั้นลง แล้วส่งให้คนอื่นๆ และการส่งให้คนอื่้นก็จะมีคนเข้ามากด อีกเป็นทอดๆ                           |
| Write QPS (สร้างลิงก์ใหม่) | 3 -5 วินาที | ไม่ควรนาน แค่การสรา้ง URL ใหม่ที่ไม่ได้ซ้ำกัน                                                                                      |
| Read QPS (คนกดลิงก์)       | 1-3 วินาที  | กดแล้วควรไปเลย ไม่ต้องค้นหานาน หากเราทำ map ดีๆ                                                                                    |
| อัตราส่วน Read : Write     | 100:1       | write ไม่น่าจะเยอะ เพราะสร้าง 1 ครั้งใช้ได้นานๆ แล้วยาวๆ                                                                           |
| Storage ต่อ 1 record       | ไม่ทราบ     | ไม่เยอะเพราะเก็บข้อมูล short_url + url                                                                                             |
| Storage รวมใน 5 ปี         | ไม่ทราบ     | หากเอาตัวเลขผมมาใส่ก็จะเป็น 200 x (365x5) = 365,000 record หาก record ละประมาณ 1-2 kb ก็จะเป็น 365,000 kb ก็ราวๆ 0.4 GB ไม่เกินนี้ |
| Bandwidth                  | ไม่ทราบ     |                                                                                                                                    |

## 5. Bottleneck & Single Point of Failure

> ขั้นตอนที่คนมักข้าม แต่เป็นตัวแยก senior ออกจาก mid-level
> **หาจุดพังในระบบตัวเองให้เจอก่อนที่คนอื่นจะถาม**

| จุดที่จะพังก่อน                      | พังตอนไหน                                                             | ถ้าเกิดขึ้นจะทำยังไง           |
| :----------------------------------- | :-------------------------------------------------------------------- | :----------------------------- |
| คนกดเข้ามาพร้อมๆกัน                  | ระบบโดน Block จาก Database หรืออะรก็คามทำให้ API รอคิวนานมาก          | ไม่ทราบ                        |
| คน Spam URL เดิมๆ ซ่ำๆ เข้ามาเรื่อยๆ | หากโดน Bot เอา URL เดิมารุมยิงเรื่อยๆก็จะทำให้ DB บวมแล้ว server load | validate url ก่อน + rate limit |
|                                      |                                                                       |                                |
